# CP-22 — M7a: the re-vendor rehearsal

You are executing CP-22 of `gsj-harness-rollout-server`. Scope: bring the
vendored Polar pin forward, re-apply the three carried patches, and measure
what it actually costs.

**Why this checkpoint exists**: A-8 ("vendoring a release-less branch is
sustainable") is the last untested assumption in the charter, and it is the
last named reversal door on CP-12's ADOPT verdict. CP-03 estimated ~half a
day per re-vendor with the mechanism proven; **no second vendor has ever
run**. This turns an estimate into a fact — or finds out it was wrong,
which is worth more.

**Freeze-lift: `vendor/**` (the tree, the patches, `POLAR_SHA`,
`REVENDOR.md`), `pins/**` (only if the re-vendor moves a pinned value —
that would itself be a finding), `docs/**`. NOT lifted: `gsj_rollout/`,
`corpus/`, `mcp-service/`, `forgejo/`, `spike/`, `tests/`. If our code
needs to change to accommodate the new pin, that is the finding this CP
exists to find — record it, do not quietly patch it. GPU, no estate, no training.** The verification is the four suites
plus the vendored tests `REVENDOR.md` makes mandatory.

Read first: `vendor/REVENDOR.md` — **this CP executes it**, and one of its
outputs is whether the recipe is still correct; `docs/reports/CP-03.md`
(the first vendor: what each patch anchors on, the adversarial FAITHFUL

ADR-0005-vendoring.md`; `docs/reports/CP-02.md` (the fork audit — the

## Step 1 — Survey before touching anything
Establish where upstream actually is now, with `gh api` (CP-02's method —
the web pages are robots-blocked, the REST API is not):

- `stable`'s HEAD and date. Has anything landed since `f0e8343a`?
- the `polar` dev branch — is the `prefix_merging` refactor still
  unlanded, has it merged, has it grown?
- the maintainer forks (`skzhang1`, `billxbf`) — anything relevant
- tags or releases — still none?
- **and specifically: is there any upstream fix for our three patches'
  subjects?** A non-agent-completion filter, an abort→ERROR path, or
  policy-version stamping landing upstream would retire a patch, which is
  the best possible outcome.

**Then decide what to re-vendor to**, and say why. The options are not
equal:
- **`stable`'s new HEAD**, if it moved — the conservative target
- **the `polar` branch**, if the refactor is the thing we need to measure
  against — the honest target, since it is the named risk and will land
  eventually
- **nothing moved** — then re-vendor to the *same* SHA, which still
  exercises the whole recipe end to end and proves the mechanism without
  the diff. Say so plainly rather than declaring the CP vacuous; a
  rehearsal that proves the recipe reproduces is a real result.

## Step 2 — Executllow the recipe as written, and **record every place it is wrong,
incomplete, or assumes something no longer true.** That is half the value
here: a recipe nobody has followed is a hypothesis.

Fetch, extract, apply patches via `apply_patches.sh`, resolve rejects.
For each patch, report: applied clean, applied with fuzz, or required
re-anchoring — and if re-anchored, what moved and whether the patch still
does what its header claims. CP-03's adversarial standard was
byte-fidelity by reverse-apply; hold to it.

**If a patch cannot be re-anchored**, that is a finding, not a blocker to
work around. Say what changed upstream that broke it and what the options
are (re-author, drop, upstream it).
