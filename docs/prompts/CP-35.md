# CP-35 — M11b: trajectories a person can read

You are executing CP-35 of `gsj-harness-rollout-server`. CP-34 gets a
stranger to a standing estate and an accepted episode. This gets them to
**seeing what the agent actually did.**

Today the receiver archives a 587 KB callback body and nothing can read
it. CP-32's stranger hand-counted. That is the gap.

**Success criterion**: from an accepted episode, a stranger runs one
command and reads a transcript of the session — the prompt, each turn,
every tool call and its result, the deliverable — and runs another and
gets a structured export a program can consume. Both derived from the
archived body, **adding nothing the receiver does not already write.**

**The discipline line, and it is the one CP-00 drew**: this reads the
archive. It does not index, accumulate, or persist. Rows 16–21 are
DROPPED and two trainers confirmed nobody needed them. The moment this
wants to store something the rollout server doesn't produce, it is
asking for the store bap and record it instead.

## Step 1 — Read a body first, then design
Open a real archived trace and write down what is actually in it: the
messages, the tool calls and results, the token arrays, the mask, the
logprobs, the reconstruction stats, the gate findings, the metadata, the
timings.

Then decide what each view carries — and say what you are **leaving
out** and why. A transcript that dumps 30,000 token ids is not readable;
a structured export that drops the mask is not usable.

## Step 2 — The readable view
A session transcript a person opens to understand the episode. At
minimum: the task (case, timestep, prompt), the system prompt (or a
statement of its hash — it is 4,466 chars), each assistant turn's text,
each tool call with its arguments, each result, the finish reason, and
the deliverable if one was written.

Three things to get right:
- **Reasoning**, when thinking is on, is *inside* the assistant turns.
  Render it distinguishably — of trainable tokens (CP-32) and
  a reader should see what the model was doing, not a wall of text.
- **The cutoff is the demo's whole point.** Every `mcp_gsj_search_case`
  result carries pages; show them, and show the episode's timestep, so
  the property is visible rather than asserted.
- **Truncation** (ADR-0025): a `finish_reason: length` episode is
  trainable and honestly labelled. The transcript should say so where a
  reader will see it, not bury it.

Plain text by default. If you add a richer format, say why.

## Step 3 — The structured view
What a program consumes: the trace fields keyed by name — ids, mask,
logprobs, prompt/response boundaries, the gate results, the
reconstruction stats, the metadata, the finish reason, the page census.

**This is not a new schema.** It is a projection of the archived body
with the giant arrays either included or referenced, your call — say
which and why. A consumer who wants the arrays already has the archive;
a consumer who wants to know *what happened* everything else.

## Step 4 — The commands
Whatever shape fits — a script in the demo repo, subcommands, a small
module. **Not a library change.** The demo owns this.

At minimum: show one episode, list what is in the archive, and something
for the quarantine (a rejected trace's findings are the most actionable
thing in the system and currently the least visible).

Every command's failure says what to do — CP-27's standard.

## Step 5 — The walkthrough
The README CP-34 deferred. Written for someone who has just run
`bootstrap.py up`: submit an episode, read it, understand what they are
looking at, and know what to do next. Include the **corpus contract**
pointer — a stranger who wants to bring their own documents needs the
shape, and CP-34's synthetic corpus is the worked example.

State the measured expectations rather than making a stranger discover
them: the cold and warm `up` timings, the disk, the qualification rate,
and — per CP-34's hunt item 4 — that a small model hits the cap on
briefand that this is visible, not broken.

## Step 6 — The endpoint question (CP-34's hunt item 1)
The smoke used the reference stack. A stranger's endpoint differs in at
least four ways that break different things: a non-vLLM tool parser,
unpinned sampling defaults, a non-Qwen tokenizer (G6's tail, the EOT id,
estate-side G4), a different context window.

**You cannot fix this here** — most of it is estate provenance. But you
can make it *legible*: a preflight that probes the endpoint and reports
what it found against what the demo assumes, with each mismatch named
and its consequence stated. A stranger should learn their tokenizer
differs before an episode is spent, not from a G6 quarantine.

Do what is cheap; wishlist what isn't.

## Step 7 — The run-through

the reference stack (which should pass — that is the control).

Then the honest question: **is the tranctually readable?** Show
an excerpt and judge it. A view nobody would open is a file, not a view.
