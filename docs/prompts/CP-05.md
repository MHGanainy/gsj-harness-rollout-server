## Step 1 — `prefix_merging.py`, line by line
This is the algorithm we are adopting. Read it end to end at the vendored
(patched) tree, and confirm or refute each property. Cite file and line for
every answer.

1. **The retokenization guarantee** — the property everything downstream
   rests on: assistant body tokens come from the **sampled response**
   (`a_m`) and are never re-derived from the next request's canonical
   rendering. Confirm in code. If there is any path where a merged
   sequence takes assistant tokens from a prompt rendering, name it.
2. **Chain partitioning** — the message-level grouping key (what it
   includes, what it deliberately ignores) and the strict token-prefix
   test. Confirm `p_{m+1}[:len(p_m)] == p_m` is an equality on token ids,
   not on text.
3. **End-of-turn detection** — `end_of_turn_token_id`: auto-detected how,
   configurable where, and what happens when detection fails or the token
   never appears in the tail.
4. **Interstitial extraction** — as implemented vs. the paper's
   §3.4.2 ("locate the first end-of-turn token `e` in the tail; if `a_m`
   already ends with `e`, `u_m` is the suffix after it, else `u_m` starts
   at that `e`"). Any divergence is a finding.
   <!-- reconstructed span: "extraction** �" → "extraction** —" -->
5. **The loss mask** — is it exactly 1-on-sampled / 0-on-interstitial, or
   are there other zeroed cases? Cross-check against CP-02's D4
   (upstream emits all-ones unconditionally at the pin — confirm that is
   still true after P1/P2 landed).
6. **The logprob array** — where `0.0` placeholders are written, whether
   they can ever land at a `mask==1` position, and what happens when the
   engine returns no logprobs at all (CP-03's `trace.json` has
   `response_logprobs: null` — explain mechanically why).
7. **What breaks a chain** — enumerate every condition, and for each say
   what the builder emits: context compaction, sub-agents, parallel tool
   calls, a harness editing earlier messages, a retry with a different
