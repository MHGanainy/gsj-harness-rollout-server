## Step 1 — ADR-0005: the vendoring mechanism
Decide and record before copying:
- **Where it lands.** `vendor/polar/` is the assumption; confirm or change
  it. State whether the vendored tree tted to this repo (yes — law
  4 says vendor, not depend, and there are no releases) and how it is
  excluded from our 1,500-line budget (the budget counts `gsj_rollout/`
  only; state it).
- **What comes.** The tree at `f0e8343a`, not the history (CP-02: 4,387 of
  4,406 commits are inherited OpenHands). Decide what to exclude —
  `.git`, their `web/` dashboard if it isn't needed, their examples if
  they are large, anything you can justify. Bias toward taking the whole
  `src/polar` tree plus what its tests and examples need; excluding too
  much makes re-vendoring harder to diff.
- **How patches are carried.** Not a fork, not a branch — a
  `vendor/patches/` directory holding `P1-non-agent-filter.patch`,
  `P2-abort-to-error.patch`, `P3-policy-version-storage.patch`, each with
  a header naming its origin SHA, what it does, why we carry it, and the
  CP-02 evidence. Plus `vendor/apply_patches.sh` that applies them in
  order against a clean vendored tree and fails loudly on a rejected hunk.
- **Thendor recipe**, written as `vendor/REVENDOR.md`: fetch the new
  SHA, extract the tree, re-apply patches, resolve rejects, run the
  verification from Step 5, update `POLAR_SHA`. Name the known risk: the
  `polar` dev branch's pending `prefix_merging` refactor (+49/−156).
- **`POLAR_SHA`** at the repo root: the pinned SHA, the date, the branch it
  came from, and the patch list.

## Step 3 — The three patches
Hand-adapt each from its fork origin (CP-02 established none cherry-pick
cleanly; fork base is `stable~2`).

**P1 — non-agent completion filter** (from `cb613pstream has **no**
such filter at all, so this is additive rather than a fix: carry the
post-fix shape test (single user message, no system, no tools, no SDK-only
keys ⇒ non-agent), not the whitelist the fork removed. Wire it where the
fork wired it. **Flag prominently** that its shape criteria were validated
against a different harness's wire dialect and must be re-validated against
pi's at CP-06 (A-12).

**P2 — abort → ERROR** (from `3c930e6d`, hunks 1–2 only; hunk 3 deletes
fork-only code that doesn't exist here). Any `finish_reason == "abort"` in
a session ⇒ `trajectory.status = ERROR` in `prefix_merging.build()`.
Verify by reading that the pin's propagation path (SessionResult.status →
bridge → FAILED → masked) is intact.

**P3 — policy-version storage half** (from `08e59e75`, the ~45 lines in
`gateway/storage.py` plus the `dict(record.metadata)` persistence fix).
Carry the stamping and persistence; do **not** carry the admin endpoint or
the entry-interception halves (CP-02: efficiencA-13
covers the interim). Note in the patch header that this is inert until a
trainer declares versions.

Each patch gets a test or an assertion proving it applied — at minimum, a
grep-level check in `apply_patches.sh` verifying the expected symbol is
present after application.

## Step 4 — Dependency reconciliation
Polar's install (Python 3.12 per their README, `sglang==0.5.13` installed
separately, uv-based) against ours (3.11+, pydantic/httpx/pyyaml core).
Decide and record:
- does `[server]` install Polar from the vendored path (editable? path
  dependency?) or do we run it from `vendor/polar` directly with its own
  environment
- which Python version the server side requires, and whether that forces
  anything on the root package
- what `[server]` actually declares now that we know the real deps
- whether sglang/vLLM are needed for the calculator example (probably not
  — it is a smoke test) and whether they are needed at all before CP-09

**Bias toward the smallest thing that works.** A separateor/polar/.venv` built from their instructions is a legitimate answer
and keeps our root install light — the mcp-service precedent (CP-01) shows
component venvs are an accepted pattern here.

## Step 5 — Prove it runs
Their calculator example, end to end: rollout server up, gateway up, submit,
get a result. Record the exact commands, the topology file used, and the
output. Then, without going near our corpus or pi:
- confirm the patched code paths are live (P1's filter is reachable, P2's
  abort check is in `build()`, P3's stamping is in storage)
- dump one real `Trace` and one real callback payload to `docs/polar/` —
  these are the artifacts CP-06 and CP-08 will build against, and having
  them now removes a guess from both
- note anything about the run that bears on our assumptions: does the
  proxy log what it captured, how are completions counted, what does
  `reconstruction_stats` actually contain

If the calculator example cannot run, that is the CP's finding: record
precisely where it fails, whit is a dependency problem or a code
problem, and stop rather than working around it silently.
