## Step 1 — The stub backend (`spike/stub_backend.py`)
A minimal OpenAI-compatible `/v1/chat/completions` server whose **only
job** is to be a dialect Polar's capture actually works against — CP-03
proved mlx-lm's does not (`{"id","logprob"}`, no `token_ids` ⇒ empty
`prompt_ids` ⇒ S1 degeneration).

Requirements, derived from `record_utils.py:82-140`:
- return `prompt_token_ids` (or `input_token_ids`) so `prompt_ids` is
  non-empty — this is what makes chain merging possible at all
- return response token ids in one of the accepted shapes: `token_ids`, or
  `logprobs.content` entries carrying a `token_id` key
- return real-looking logprobs (finite, ≤ 0), one per response token
- honor tool calls well enough that pi takes multiple turns: the stub
  should emit a tool call on early turns and a final answer on the last,
  so the session produces a **multi-completion chain** rather than one
  completion per turn
  <!-- reconstructed span: the original read "…a **multi-completion
       chain** rather urn" -->
- be deterministic and dependency-light (stdlib or fastapi — no model)

**Sanity gate before anything else:** a two-turn stub session through
Polar must produce `chains_total == 1`. If it produces N length-1 chains,
the stub's dialect is wrong and every later observation is worthless —
fix the stub, not the conclusion.
