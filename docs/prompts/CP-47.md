## Step 1 — The two axes, and why one is not enough
Classify on **two** independent axes, because collapsing them produces a
hide list that breaks the build:

**Axis 1 — audience.** Who is this for?
- **CONSUMER** — someone who installs and uses the library
- **OPERATOR** — someone standing an estate up
- **CONTRIBUTOR** — someone changing the code
- **INTERNAL** — the development record; serves the project, not a user

**Axis 2 — coupling.** What breaks if it is not in the repository?
- **RUNTIME** — code reads it when something runs (CI, the pins walk,
  a test, the build)
- **DERIVED-FROM** — its bytes determine a value committed elsewhere
  (a lock SHA, a pin, a wheel hash)
- **CITED** — referenced by path from material that must keep resolving
- **FREE** — nothing reads it, nothing depen it
  costs only the information in it

**The interesting cells are the contradictions**: INTERNAL + RUNTIME,
INTERNAL + DERIVED-FROM. Those are files that look like process and
behave like dependencies. Name every one — that list is the reason this
CP exists rather than a `.gitignore`.

## Step 2 — Classify, exhaustively
Every tracked path. Directories may be classified as a unit **only if
every file in them shares both axes** — otherwise break them out. State
which directories you split and why.

Expected to need splitting, based on CP-46: `docs/` (normative documents
vs the record vs runtime-read evidence), `corpus/` (the pipeline vs the
staging tree), `pins/` (approved sets vs derivation scripts vs captured
artifacts).

Per row: path, file count, audience, coupling, **and one line on what
reads it or depends on it** — with the citation. "Nothing reads it" is a
claim and needs to be checked, not assumed.

## Step 3 — The evidence for coupling
For every RUNTIME and DERIVED-FROM classification, soof:

- the file:line that reads it, or
- the value it determines and where that value is committed

CP-46 found CI's fixture, `derive_pins.py`'s two reads, and seven
`pathlib` test constants. **Find the rest.** Grep for path literals
across workflows, scripts, tests, and the library — and check the
consumer repos too, since they read library fixtures.

If a RUNTIME read turns out to be avoidable (a fixture that could be
copied), say so and what it would cost.

## Step 4 — The consumer's repository, hypothetically
Given the classification: **what would a repo containing only
CONSUMER-facing and FREE-coupled files look like?**

- the file listing
- what a consumer loses (be specific — the audit? the ADRs? which?)
- what breaks (name every RUNTIME and DERIVED-FROM row that would have
  to move with it or be re-homed)
- what the README's evidence table cites that would no longer resolve

**Do not build it.** Describe it, so the operator can see the trade
before paying for it.

## Step 5 — The options, gainst the classification
Three, at least, each priced from Step 2's counts rather than by
feeling:

- **(a) Split** — internal files to a second repository, public or
  private. Cost: the RUNTIME/DERIVED-FROM re-homing, the citation
  rewrites (CP-46 counted 740), history extraction to keep commit
  anchors resolving, and every future CP writing to two repos.
- **(b) Untrack** — internal files removed from `HEAD`, kept locally.
  Cost: the same re-homing, plus the record stops being checkable by
  anyone but the operator, plus one disk failure from gone.
- **(c) Frame harder** — CP-46's approach extended: per-directory
  READMEs, a top-level map, the classification itself published so a
  reader knows what to skip. Cost: near zero, fixes the listing's
  legibility but not its length.

For each, state honestly what it does and does not achieve **against
the operator's stated requirement** — hiding internal development
material from a consumer.

## Step 6 — Recommend, and stop
One recommendation, ing, its cost. Then stop.

**Do not act on it.** The operator decides with the table in hand.
