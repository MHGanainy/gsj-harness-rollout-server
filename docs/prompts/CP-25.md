## Step 1 — Read the config as a stranger, and write down every friction
Before changing anything. Open `rollout.h200.yaml` and ask, per line:
*could someone who has read only the README know what to put here?*

Expect to find: in-image paths a consumer can't know, token ids that came
out of a pins walk, a `builder.strategy` import path, endpoint values
tangled with tuning values, and things estate facts rather than
choices. **List them.** That list is the CP's actual subject.

Then classify every key: **endpoint** (a consumer must supply),
**tuning** (a consumer may change), **estate fact** (derived — should
have a default or come from elsewhere), or **lore** (should not be in the
file at all).

## Step 2 — The config a stranger can fill in
Reshape toward: the things a consumer must supply are few, obvious, and
at the top; everything else has a working default and a comment saying
what it is.

Constraints that do not bend:
- `extra="forbid"` stays. Unknown keys still raise naming section+key.
- The `user:` free-form section stays untouched and unread.
- Nothing becomes *unrepresentable* that an estate legitimately needs —
  `runtime.workdir` stays unrepresentable (CP-06's trap), but a value
  with a good default is not the same as a value removed.
- **Defaults must be honest.** A default that is right for this estate
  and wrong elsewhere is worse than a required field — CP-19's packans are the precedent, and they earned a warning for exactly this.

Where a value is genuinely derived (the glue ids are dormant since
CP-04′; the EOT id comes from a tokenizer; the builder strategy is ours),
prefer a default over a required field, and say in the comment where the
value came from.

Ship a **commented example** — the file a consumer copies. It is the
deliverable of this step, and it should read as documentation.

## Step 4 — `train.py` a person can read
Today's `cp21_loop/train_one_step.py` is ~300 lines mirroring verl's fit
loop, and `cp17_loop`'s is its slime counterpart. A consumer's script
should be short enough to read in one sitting: collect, convert, train,
sync — with the machinery behind imports.

Two constraints:
- **The three assertions stay live and visible.** They are the reason the
  bridges exist; a consumer should see them, not inherit them silently.
- **Don't hide what CP-17 and CP-21 learned.** uid grouping (F-10),
  reward attach (F-02), the measured replay floor, entropy/KL control —
  each is either in the script with a comment or in the run book with a
  pointer. Silently defaulting them is how a consumer trains on raw
  rewards while thinking they're doing GRPO.

If the honest shape is "a short script plus a well-docd module
beside it," that is fine — say so rather than compressing for the metric.
