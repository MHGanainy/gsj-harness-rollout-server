## Step 1 — ADR-0008: the four surfaces
Decide and record before writing.

- **`config.py` — one YAML, two audiences.** The file configures *our*
  rollout server; Polar's `topology.yaml` stays Polar's. Decide the seam:
  does our config generate the Polar topology and task requests, or sit
  beside them? **Recommendation: generate.** A consumer should write one
  file; we render Polar's from it. Sections: `estate` (Forgejo base +
  clone pattern, MCP base URL + token secret env, serving base URL +
  model), `runtime` (image, network, workdir rule from CP-07), `hthe ADR-0006 settings keys — roster, context window, pi paths),
  `builder` (strategy = our subclass, `end_of_turn_token_id`,
  `generation_prompt_glue_ids` — both model-specific per CP-07),
  `polar` (rollout/gateway host+port+public_url), and `receiver`
  (bind, where traces land). Plus a reserved free-form `user:` the
  library validates as a mapping and never reads — the predecessor's §9
  pattern, and the thing that lets a trainer keep its knobs in the same
  file.
- **`receiver.py` — validate the POSTed body.** CP-07 finding 5 is
  binding: the on-disk `ses_*.json` is *not* the callback payload. The
  receiver accepts `POST /callbacks/session_result`, runs `checks` over
  the body, and either persists the trace or rejects it loudly. Decide:
  where do accepted traces land (a directory of JSON? one file per
  session?), what happens to rejected ones (dropped with a counter and a
  log line, or quarantined to a separate path — **recommendation:
  quarantined, because forensics beat counters** the receiver
  returns to Polar in each case.
- **`client.py` — the trainer's whole surface.** Submit tasks, wait,
  return validated traces. It must run **the same `checks`** the receiver
  ran (law 6: trust nothing across the wire). Decide the shape:
  `RolloutClient(base_url).collect(tasks, ...) -> list[Trace]` is the
  obvious one; state whether it polls `GET /rollout/task/{id}` or reads
  the receiver's output, and why.
- **`cli.py` — `gsj-rollout serve | submit`.** `serve` brings up what?
  Polar's rollout server and gateway are separate processes with their
  own CLI; decide whether we supervise them, print the commands, or
  require them running. **Bias toward the smallest honest thing** — a
  `serve` that starts our receiver and tells the operator the two Polar
  commands is more maintainable than a process supervisor, and the
  predecessor's `gsj-collect` lesson (F-08/F-14/F-17) was about
  *observability and bounded exit*, not about owning process lifecycle.
  Whatever you choose: bounded progress output, signals that
  actually stop it.
- **`__init__.py`** — the consumer surface. `RolloutClient`, `Trace` (or
  our wrapper), `checks`, `load_config`, `RunConfig`. Deliberately not
  exported: the harness and builder (they are loaded by Polar via import
  path, not called by consumers).

## Step 2 — Implementation
Per the ADR. Two constraints from the charter:

- **`checks.py` stays a stub.** Define its *interface* now — the
  signature the receiver and client both call, and the shape of what it
  returns (findings list? raise? both?) — and have it return "no
  findings" unconditionally with a docstring saying CP-10/CP-11 fills it.
  Getting the seam right now and the rules later is the whole point of
  splitting them.
- **Nothing in `gsj_rollout/` assumes Docker** (law 5). The runtime is a
  config value.

## Step 3 — Collect-N semantics (gap row 26)
The predecessor left this ambiguous and it bit twice: `truncated` counts
toward a collection target but may not satisfy the consumer's tate ours explicitly in `config.py` and the CLI's `--help`:
- what counts as a *collected* trace (accepted by checks? any terminal
  status? excluding ERROR?)
- what `submit --episodes N` targets
- what happens when a trace is rejected — does it count, does it retry
Write it down; do not inherit the ambiguity.

## Step 4 — Tests
No GPU, no estate. Fixture-driven:
- **the real callback body** (`docs/polar/pi-corpus/
  callback_session_result.json`) round-trips through the receiver:
  accepted, persisted, the trace readable
- a **doctored** body (builder ERROR status; or findings present in
  `gsj_validation`) is rejected and quarantined, not persisted
- config: full-file round-trip; unknown key in a library section raises
  naming section+key; `user:` free-form accepted and never read
- config → Polar topology + task request rendering (golden-file compare,
  since CP-09 depends on these being right)
- client: `collect()` against a fake receiver/rollout endpoint returns
  traces and runs `checks`; **asshecks` is called on the client
  side too** (law 6's teeth)
- CLI: `--help` exits 0, `submit` with a bad config exits with the stated
  code, bounded exit works, **no signal handler installed at import**
  (the predecessor's embeddability property)
