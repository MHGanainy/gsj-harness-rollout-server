## Step 1 — ADR: the pins decision
The load-bearing choice, and it must be made explicitly.

`pyproject.toml` currently force-includes `pins/pins.gsj.json` as package
data so `checks` works out of the box (CP-16, proven in CI every push). On
PyPI that means **a stranger's default approved set is this estate's
hashes**. It fails loudly — approval is set membership, so a foreign
estate gets `*_not_approved:<digest>` rather than a silent pass — but it
is confusing, and it invites someone to believe the library ships
meaningful defaults.

Three options; decide and record:
- **ship as-is** — the trainer leg works on install, at the cost of the
  confusion above
- **ship empty** — `GSJ_PINS_PATH` becomes mandatory, with a clear error;
  honest, but it breaks CP-16's out-erty and the CI proof
  that guards it
- **ship as-is with a loud signal** — the packaged set is used, and the
  library says so once, naming `GSJ_PINS_PATH` and stating that these are
  the reference estate's values

**Recommendation: the third**, because it preserves the property CP-16
built and CI proves while making the situation unmistakable. If it needs a
one-line log or docstring change in `gsj_rollout/`, that is the one source
edit this CP may make — declare it, keep it to the signal, and change no
rule.

Also decide: does the packaged set stay in sync with `pins/` (it is
force-included from there, so yes by construction) and what happens at a
re-pin — nothing, or a rebuild.

## Step 2 — Metadata
CP-18 named the gap: no `readme`, no `license`, no classifiers, no URLs.
Fill it, minimally and accurately:

- `description` — one line that says what this is. "A rollout server for
  agent RL" or similar; it is what PyPI shows in search results.
- `readme` — point at `README.md`. Read it first nding page
  rather than a repo front door; the badge and caption are fine, the
  checkpoint numbering may not be. Decide whether it needs a short
  preamble for someone arriving cold.
- `license` — **this is a real decision, not a formality.** The repo
  vendors Polar (Apache-2.0) and depends on a corpus and estate that are
  yours. Pick a license, add the file, and state the reasoning. Note that
  `vendor/polar/` carries its own license and is not covered by yours —
  say how that is expressed (it stays out of the wheel; verify).
- `classifiers` — Python version, license, development status, intended
  audience. Keep it short and true; `Development Status :: 4 - Beta` is
  probably honest.
- `urls` — repository, and the docs that matter (`docs/VERDICT.md` is the
  document a stranger should read first).
- `requires-python` — currently `>=3.11`, and CI tests 3.12 only. Either
  test 3.11 or narrow the claim. **Narrowing is the simpler honest
  move**; say which you took.

## Step 4 — The release workflow
A second workflow, separate from CI. Trigger on a tag (`v*`), not on push
to main.

- **`permissions:`** — CP-18 deliberately omitted one because no job used
  the token. This workflow needs it, least-privilege. If you use trusted
  publishing (recommended — no API token to store or rotate), that means
  `id-token: write` and a PyPI publisher configured for this repo.
- It should **not** duplicate CI on the tests having passed, or
  re-run the wheel job only; do not rebuild the whole matrix.
- It should publish to **TestPyPI first**, or at minimum have a documented
  dry-run path. A first upload that is wrong is not revocable — PyPI does
  not allow re-uploading a version.

State plainly what the workflow does and does not do, the same way CP-18's
header does.
