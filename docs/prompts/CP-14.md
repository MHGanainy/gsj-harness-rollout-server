# CP-14 — M4b: split-by-directory

You are executing CP-14 of `gsj-harness-rollout-server`. Scope: make the
train/eval split a property of the corpus tree rather than a manifest key,
and carry it through the taskbank row into the trace.

**No GPU, no estate, no Chroma (CP-15), no re-collection.**

**Freeze-lift: `corpus/**` (contract, pipeline, staging tree),

NOT lifted: `pi_harness.py`, `builder.py`, `receiver.py`, `client.py`,

## Step 1 — ADR-0015: the contract change
Decide and record before touching the tree.

- **The shape.** `<corpus-root>/{train,eval}/cases/<case_id>/timestep-<T>/…`
  Confirm or improve. Corpus-level files (`corpus.yaml`, `AGENTS.md`,
  `skills/`) stay at the root, above the split — they are shared.
- **`eval_case_ids` retires.** Split was a manifest key and becomes a
  directory. The validator must **reject** a corpus still carrying the
  key, with a message naming the migration. Silently ignoring it is how a
  data-prep team ships a corpus whose split means nothing.
- **Exactly one split per case.** A `case_id` under both is a hard
  validation failure; state the message.
- **Two splits, named** — `train` and `eval`, no third. If `test` ever
  earns its keep it gets its own ADR. Record that the door is
  deliberately copened.
- **What the split means downstream, honestly.** It rides the taskbank
  row, `TaskRequest.metadata`, and the trace. State plainly what
  *enforces* it: nothing here does. The predecessor's loader had a role
  lock; this repo dropped the loader at CP-00. So the split is **carried
  and visible, not enforced**, and the trainer owns not training on eval.
  An unenforceable guarantee stated as a guarantee is worse than an
  honest label.
- **Is this new capability or a clarification?** `corpus.yaml`'s
  `eval_case_ids` already expressed case-level split. Say which — the
  data-prep doc should describe one mechanism, not two.

## Step 2 — The pipeline
`corpus/ingest_corpus.py`, per phase:

- **validate**: split directories, exactly-one membership, the retired-key
  rejection, plus every existing per-case/per-timestep rule unchanged. The
  PASS table gains a split column.
- **scaffold**: unchanged in output — a case repo is split-agnostic
  (ADR-0006). Say so, so nobody expects `gsj-staging/train/c01`.
- **taskbank**: still raises (ADR-0003). But specify the split's path into
  a row *now* — which field, what values, case-level — so the deferred
  implementation has no decisions left.
- **verify**: the split checks back from the lock; a case that moved
  splits without the lock changing is a mismatch.
- **`corpus.lock.json`**: gains the split per case. Its bytes and sha
  change — a re-derive, not a re-pin. Enumerate which artifacts move and
  which don't.

## Step 3 — Re-shape the staging corpus
Move `corpus/staging/cases/*` under `train/` and `eval/` per the current
`eval_case_ids` (case_0004 eval, the rest train — verify against the
manifest rather than trusting this sentence), then retire the key from
`corpus.yaml`.

**The page bytes must not change.** Assert it: every
`timestep-<T>/pages/*.md` is byte-identical before and after the move.
That is what keeps the case repos' scaffolded SHAs reproducible —
`corpus.lock.json`'s ref SHAs should be unchanged by the move, and only
the new spould differ. If any SHA moves, stop: something
touched content, and the whole determinism story rests on it not having.

Run `validate` and `verify` after. The taskbank's frozen
`taskbank.parquet` (sha `9eb8e3c2…`) is carried data, not regenerated
here — confirm it still verifies.

## Step 4 — Split into the task request and the trace
`config.py:render_task_request` gains `split` in `TaskRequest.metadata`,
alongside `case_id`/`timestep`/`prompt_source`. It rides the CP-11-proven
channel to trace metadata.

Where does the value come from? The submit path knows the case; the split
lives in the corpus lock. Decide: a parameter (like `prompt_source`), or
resolved from a lock the config points at. **Prefer the parameter** — the
config surface should not grow a corpus dependency, and the taskbank will
supply it when ADR-0003 lands. State the default and what it means when
absent.

Then decide whether a check lands. Options, and pick with reasoning:
- **nothing** — the split is a label the trainer reads;an
  enforce what this repo doesn't own
- **a stated-value check** — the trace's split is one of `{train, eval}`
  and matches the task request, catching a malformed submit but nothing
  else
- **cross-sourced** — if the harness's workspace probe could state the
  split independently, it could be cross-checked the way CP-13a
  cross-checks branch against timestep. Note the case repo is
  split-agnostic, so there is probably nothing to cross-source *from*.
  Say so if that's the finding.

Whatever you choose, the reasoning goes in the spec. A check that only
verifies the submitter agrees with itself should be named as such.
