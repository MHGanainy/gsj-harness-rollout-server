## Notes

### The route decision, and what was actually found in uni-agent (Step 1)

**Direct.** Both source trees were read at their pins before any bridge
code existed (uni-agent @ `73b0f41`, the predecessor's pin; verl @
`1ae9455`, uni-agent's own submodule pin — so the verl examined is the
verl that path speaks). Three findings settle it, each with the file
open:

1. **uni-agent never hands verl a batch.** Its trainer-side entry point
   `OpenAICompatibleAgentFramework.generate_sequences(prompts:
   TensorDict) -> None` (`framework.py:384`) drives its own gateway
   sessions and returns `None`; per-trajectory fields go to
   **TransferQueue** as UNPADDED 1-D tensors
   (`_trajectory_to_tq_field_and_tag`, `framework.py:910–1001`). The
   padded `[B, L]` batch the CP asks for is assembled inside verl's
   TQ-mode trainer, not anywhere in uni-agent — the segment offered for
   reuse does not contain the batching.
2. **Its input type lives in the capture layer.** The segment consumes
   `Trajectory` — imported from `uni_agent.gateway.session`
   (`framework.py:23`); the class takes a `gateway_manager` as its first
   constructor argument. Feeding it externally-produced trajectories
   means importing the gateway package and instantiating the Framework —
   the two things the route's own discipline excludes. (Mechanically a
   stub + monkeypatched `tq` can drive the private method — uni-agent's
   own CPU test does — but that is faking its delivery infrastructure,
   not reusing a conversion.)
3. **What reuse would buy is ~90 lines of key-naming** whose conventions
   verl's own agent-loop worker states independently. Reading both gave
   the direct bridge two in-tree confirmations of every key it writes.

**The standing question (VERDICT: "the predecessor's uni-agent path
already speaks verl"), answered plainly: it cannot be fed
externally-produced trajectories as-is.** No offline/replay seam exists;
the entry point generates rather than ingests; the output side presumes
a live TransferQueue inside the trainer's Ray cluster. What the
intuition was pointing at is real but narrower: uni-agent's
per-trajectory field schema IS essentially our trace (flat id/mask/
logprob lists) — the *contract* transfers; the *plumbing* does not.

**The finding that generalizes it (F-11)**: verl at this pin is
mid-migration. `main_ppo` defaults to the **v1 TransferQueue trainer**
(`trainer.use_v1: true`), whose records are unpadded nested tensors
written by clients that must run inside the trainer's Ray cluster after
`tq.init()`, under trainer-minted uids and an unconditionally-read tag
schema — **externally-built batches cannot enter it either**. The padded
`DataProto` this bridge builds is the classic (`main_ppo_v0`) contract:
deprecated upstream, still documented, and the only batch an external
process can hand a verl trainer. So the boundary story sharpened:
neither uni-agent nor verl's own default pipeline accepts trajectories
from outside its process boundary; the consumable seams are the classic
batch (this bridge) or a custom `AgentLoop` returning `AgentLoopOutput`
— in which case verl drives generation and does this bridge's padding
itself (a named CP-21 option, run book item 1).

### The conversion table (Step 2)

Callback-shaped mapping → verl `DataProto` (classic batch contract, read
from `agent_loop.py::_agent_loop_postprocess`/`_postprocess`; uni-agent's
field builder names the same keys):

| Trace/body field | DataProto key | Rule |
| --- | --- | --- |
| `prompt_ids` | `prompts` [B, P] · left half of `input_ids` | verbatim ids, LEFT-padded to `prompt_length`, never retokenized |
| `response_ids` | `responses` [B, R] · right half of `input_ids` | verbatim ids, RIGHT-padded to `response_length`; the split is the fixed offset P for every row |
| `loss_mask` | `response_mask` **and** `loss_mask` [B, R], equal | builder's mask verbatim (never inferred); absent → all-zero; zeroed wholesale on non-COMPLETED/errors/findings. Two keys because the generations load-bear different ones (classic losses: `response_mask`; v1 engine normalizer: `loss_mask`) — verl's own TQ writer and uni-agent keep them equal too |
| `response_logprobs` | `rollout_log_probs` [B, R] f32 | behaviour-policy values, asserted at ingest; 0.0 at pads/inert paths; bypass-mode rollout correction copies this array INTO `old_log_probs` |
| `reward` | `rm_scores` [B, R] f32 | evaluator's value at the LAST REAL response token (verl's own placement: `attention_mask[:, P:].sum(-1) − 1`); `null` → 0.0 (F-02) |
| — (derived) | `attention_mask` [B, P+R] | 1 exactly on real tokens |
| — (derived) | `position_ids` [B, P+R] | verl's own `compute_position_id_with_mask` — clip(cumsum−1, min 0), left pads at 0, contiguous across the split |
| session identity | `uid` (non-tensor) | THE advantage-group key (GRPO/RLOO group by it); default = session id — accept only after reading F-10 |
| statuses/findings/stats | `status`, `masked_reason`, `gsj`, `polar` (non-tensor) | audit trail; fail-closed — only COMPLETED×COMPLETED trains; `finish_reason=="length"` → TRUNCATED, still trainable (CP-17 trained one live) |
| — | `meta_info` | widths, pad id, `oversize_dropped` — dropped wholesale, never clipped, never silent |

**Advantages: not produced — rewards are.** verl computes advantages
inside its fit loop from `rm_scores` → `token_level_scores` →
`token_level_rewards` → the config-owned estimator registry, grouped by
`uid`. Producing advantages bridge-side would bypass
`algorithm.adv_estimator` and re-own exactly the numerics class F-08
caught a vendored post-processor getting wrong. **`old_log_probs`: not
produced** — the trainer recomputes it with the actor's own forward pass
(decoupled), or aliases `rollout_log_probs` into it (bypass); the CP's
"verl wants old_log_probs" resolves to "verl wants the honest
behaviour-policy array under `rollout_log_probs`", which is what ships.
**Status → maskability: verl's own mechanism, not an invention** — an
all-zero `response_mask` row gets advantage 0 (the estimator broadcast
multiplies by the mask) and contributes exactly 0 in every `agg_loss`
mode (token-mean sums under the mask; seq-mean modes exclude
fully-masked sequences); verl itself neutralizes rejection-sampled and
synthetic-padding samples this way, and the agent-loop path has no
sample-drop status key to use instead. A session with no usable trace
contributes nothing — verl has no group-shape constraint needing slime's
`remove_sample` placeholder, so F-05's hardcoded `tokens=[0, 0]` has no
counterpart here.

### The padding test, verbatim (Step 5)

```python
def test_unequal_length_batch_pads_without_corrupting_alignment(
        cp09prime_body, cp07_body):
    """Three real-shaped rows of very different lengths (3990 / 7196 / 100
    response tokens) in one batch: every row's mask and logprobs must sit
    at ITS OWN offsets, verbatim, with zeros exactly where padding is —
    this is the failure mode slime's per-sample shape never had."""
    short = _shortened(cp09prime_body, keep=100)
    records = (_ingest(cp09prime_body, uid="a")
               + _ingest(cp07_body, uid="b")
               + _ingest(short, uid="c"))
    assert [len(r.response_ids) for r in records] == [3990, 7196, 100]
    data = bridge.build_batch(records)
    R = data.meta_info["response_length"]
    P = data.meta_info["prompt_length"]
    assert R == 7196 and len(data) == 3

    for row, record in enumerate(records):
        n_response = len(record.response_ids)
        n_prompt = len(record.prompt_ids)
        # response block: ids, mask, logprobs verbatim at [0, n) — then pad
        assert data.batch["responses"][row, :n_response].tolist() == record.response_ids
        assert data.batch["response_mask"][row, :n_response].tolist() == record.response_mask
        assert data.batch["rollout_log_probs"][row, :n_response].tolist() == pytest.approx(
            record.rollout_log_probs)
        assert int(data.batch["response_mask"][row, n_response:].sum()) == 0
        assert float(data.batch["rollout_log_probs"][row, n_response:].abs().sum()) == 0.0
        # prompt block: left-padded, ids flush right
        assert data.batch["prompts"][row, P - n_prompt:].tolist() == record.prompt_ids
        assert int(data.batch["attention_mask"][row, :P - n_prompt].sum()) == 0
        # the fixed split: this row's response really starts at column P
        assert data.batch["input_ids"][row, P:P + n_response].tolist() == record.response_ids
        # attention is 1 exactly on real tokens
        assert int(data.batch["attention_mask"][row].sum()) == n_prompt + n_response

    # per-row trainable totals survived the stacking
    assert data.batch["response_mask"].sum(dim=1).tolist() == [
        sum(record.response_mask) for record in records]
    # and the CP-07 row is the masked one (its gates fail), not a shifted one
    assert data.non_tensor_batch["masked_reason"][1].startswith("findings:")
    assert int(data.batch["response_mask"][1].sum()) == 0
```

Backing it: `build_batch` itself asserts the stacking invariants at
construction time (`_assert_padded_alignment`: padding may not
manufacture trainable positions or non-zero logprobs; the mask may not
shift), the layout test proves left/right pad sides and the fixed split
against a forced-padding width, the position-ids test proves equality
with verl's own helper on a left-padded row, and the ERROR-session test
runs verl's `compute_grpo_outcome_advantage` and `agg_loss` (all three
agg modes) on a mixed batch to show the masked row contributes exactly
zero. Oversize traces: dropped wholesale, never clipped, recorded in
`meta_info["oversize_dropped"]`, and an all-dropped batch raises.

### verl's estimator against F-08 (Step 4, the named question)

**verl does not have the F-08 shape — structurally, not by luck — and
the answer is test-pinned, not just read.**

- `compute_grpo_outcome_advantage` (`core_algos.py:326`) contains the
  textually identical epsilon-floored division `(score − mean)/(std +
  1e-6)`. The structural difference: its std is over the **whole uid
  group, self included**, where slime's vendored LOO scale is
  `stdev(others) + 1e-6`. Consequence: `std == 0` implies every
  deviation is exactly 0, so the `1/ε` factor only ever multiplies zero
  — `0/ε = 0`, never `1/ε = 1e6`. With the CP-17 distribution (1
  rewarded in 27, one group) the max advantage is **≈5.0** where slime's
  measured 1e6; with all-identical rewards the advantages are exactly 0.
  Pinned: `test_f08_shape_verl_grpo_is_structurally_immune`.
- verl's actual leave-one-out estimator,
  `compute_rloo_outcome_advantage` (`core_algos.py:588`), centres by the
  LOO mean and **divides by no variance at all** (its `epsilon`
  parameter is dead code) — the F-08 mechanism has no counterpart to
  fire. Pinned: `test_verl_rloo_has_no_variance_division`. The sweep
  extends across the registry: pass@k and GDPO reuse the inclusive-std
  shape; OPO does no std division.
- **The new hazard found instead (F-10)**: verl hardcodes `mean 0.0 /
  std 1.0` for a uid group of ONE (`core_algos.py:315-317`), so a
  singleton group's advantage is its RAW UNCENTRED reward. The bridge's
  default uid (= session id) makes every group a singleton at CP-17's
  collection shape — a naive loop would train on raw rewards while
  looking like GRPO. Pinned:
  `test_singleton_uid_group_gets_raw_reward_advantage`; grouping is run
  book item 5. Adjacent (F-11 note): OPO — non-default — NaNs on a uid
  group whose members are all fully masked; GRPO/RLOO are immune, and
  the bridge warns loudly on an all-masked batch.
