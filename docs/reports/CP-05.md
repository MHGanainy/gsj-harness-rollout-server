#### Step 1 — `prefix_merging.py`, property by property

All citations are into `vendor/polar/src/polar/trajectory/` unless noted.
Every property below was independently re-derived by an adversarial
verifier; verdicts noted where they corrected the first read.

**1. The retokenization guarantee — CONFIRMED.** Assistant tokens enter
the merged stream only via `_append_response_tokens`
(`builder/prefix_merging.py:337-353`) from `trace.response_ids`, which
`record_utils._extract_response_tokens` (`builder/record_utils.py:82-107`)
takes exclusively from engine-sampled fields: `choice.token_ids` /
`response.token_ids` (int-coerced, `:87-88`), the `logprobs.content`
pairing (requires the `token_id` key, `:23-47`), or sglang
`meta_info.output_token_logprobs` (`:50-79`) — else `[]`. No tokenizer is
imported anywhere in the builder (grep: zero hits); no path tokenizes
message text. The canonical copy of the previous assistant body inside
`C_{i+1}.prompt_ids` is deliberately skipped by `_slice_interstitial`
(`:326-334`). **There is no path where merged assistant tokens come from
a prompt rendering.** Two capture-side caveats that do not break the
guarantee but gap the stream: a mid-chain completion with empty
`response_ids` contributes nothing while its canonical body is *also*
skipped (S6 below), and only `choices[0]` is ever read
(`record_utils.py:131-134` — S8).

**2. Chain partitioning — the message-level grouping key DOES NOT EXIST
at the pin.** Grouping is purely the token-prefix test: the build loop
(`prefix_merging.py:121-129`) calls only
`_find_extendable_chain(prompt_ids, chain_tips)`, whose sole test is
`0 < n <= len(prompt_ids) and prompt_ids[:n] == tip` with longest tip
winning (`:397-401`) — an equality on token-id **list slices**, not on
text. Confirmed: `p_{m+1}[:len(p_m)] == p_m` on ids. The builder
README's "a message-level key gates candidates first … deliberately
ignores tool-result and empty assistant messages"
(`builder/README.md:28-29`) describes machinery that is absent from the
code — a README-vs-code divergence, most plausibly documentation of the
unlanded `polar`-branch refactor (ADR-0004's named re-vendor risk). Minor:
`prompt_ids` are taken as-is from JSON, **not** int-coerced
(`record_utils.py:147`), unlike `response_ids`.

**3. End-of-turn detection.** Configurable per task:
`TaskRequest.builder.config.end_of_turn_token_id`
(`rollout/models.py:68` → `registry.py:38` `cls(**spec.config)` →
`prefix_merging.py:81-86`). Auto-detect (`:286-302`): the **last sampled
token of the FIRST completion in the chain** whose `finish_reason` ∈
`{stop, tool_calls, stop_sequence}` (`:52`) with non-empty
`response_ids`; resolution is **per-chain** (`:184`). Detection fails
(returns None) → `_slice_interstitial` returns None (`:326-327`) → the
merge loop breaks (`:230-239`) → **every ≥2-completion chain truncates at
its first merge step, silently, status COMPLETED** (only a
`logger.debug` and `chains_reconstructed_truncated`). Token never in the
tail → `ValueError` → same break (`:328-331`). **New (S5, missed by the
first read, found by the critic): detection can SUCCEED with the wrong
token** — an OpenAI-format `stop` also fires on a user-supplied stop
parameter (and `stop_sequence` is exactly that), making the last sampled
token arbitrary; `.index(wrong_id)` then mis-splits every tail,
duplicating assistant-body fragments into the stream as mask-0 tokens or
swallowing real interstitial — corrupted-but-COMPLETED with clean stats.
Hence A-15: gsj rollouts always pin the id; the builder subclass rejects
when unset.

**4. Interstitial extraction vs the paper's §3.4.2 — FAITHFUL.**
`_slice_interstitial` (`:304-334`): `k = canonical_tail.index(eot_id)` —
the FIRST end-of-turn token (`:329`); if `prev_raw_response` ends with
`e`, return the suffix AFTER it (`canonical_tail[k+1:]`, `:332-333`);
else return `canonical_tail[k:]` — `u_m` starts AT `e`, which enters the
stream as a mask-0 token (`:241-244`). Exactly the quoted spec; no
divergence. The None path (unknown/absent `e` → break → truncated) is an
implementation addition the quoted paper text does not cover — behavior:
drop the tail, stay COMPLETED.

**5. The loss mask — exactly 1-on-sampled / 0-on-interstitial, no other
zeroing.** `build_trace_from_completion` emits `[1]*len(response_ids)`
unconditionally (`record_utils.py:149`); `_append_response_tokens` keeps
it or falls back to all-ones (`:346-349`); interstitials get `[0]*len`
(`:244`). **CP-02's D4 cross-check: still true after P1/P2** — grep for
reasoning masking over the patched tree: zero hits; P1/P2 touch neither
site. Trainer-side only, slime zeroes the whole mask for ABORTED/FAILED
samples (`slime_bridge/adapter.py:128-129`). One wire-contract hole: the
`Trace` validator skips the length check when the mask is **empty**
(`models.py:116`) — an N-token trace with no mask validates; `checks.py`
must not inherit that (spec rule added).

**6. The logprob array.** `0.0` placeholders are written only in
`_finalize_logprobs` at None slots (`:368`) — and any None slot at a
`mask==1` position nulls the **entire array** first (`:364`), so **a
placeholder can never land at `mask==1`** (verifier CORRECTED scope only:
`adapter.py:219,279` also writes 0.0s, likewise never at trainable
positions — a raise at `:274-278` fires first). A **genuine**
engine-reported `0.0` at `mask==1` passes through untouched — our
suspicious-zero rule stays load-bearing. Engine returns no logprobs at
all → all slots None → `:362` returns None. That mechanically explains
`trace.json`'s `response_logprobs: null`: mlx-lm's entries are
`{"id": 27, "logprob": -1.48}` (verified in
`docs/polar/completion_record.json`) — the required `token_id` key is
absent (`record_utils.py:38`), no `token_ids` field exists, so
`_extract_response_tokens` returns `([], None)` (`:103-107`) and the
slot list is empty.

**7. What breaks a chain — the enumeration.** Two distinct layers:
grouping-time (a fresh chain; no stat marks it) and finalize-time (a
truncation; `chains_reconstructed_truncated += 1`, tail dropped). Status
is COMPLETED in every case below except abort.

| condition | layer | mechanism | builder emits |
|---|---|---|---|
| context compaction | grouping | prompt no longer prefix-extends any tip → fresh chain (`:123-127`) | 2+ chains, each can count "full"; COMPLETED |
| harness edits earlier messages | grouping | same as compaction | same |
| sub-agent, distinct prompt prefix | grouping | own chain — by design (docstring `:12-21`) | one chain per conversation |
| sub-agent seeded with the parent's full history | grouping | extends the parent's tip and REPLACES it (one tip per chain, `:129`) — the parent's next turn no longer extends and starts a new chain | parent chain split/hijacked; all pieces look clean |
| parallel tool calls in one turn | — | not a break: one completion; next prompt appends all results; prefix holds | normal merge |
| retry, different seed, same prompt | finalize | equal tip passes grouping (`:399`); canonical tail is empty; `.index` raises → None → break (`:328-331`, `:230-239`) | retry + everything after dropped; truncated += 1; first attempt trained; COMPLETED |
| **degenerate case (CP-03 live)** | grouping | **confirmed in code**: empty `prompt_ids` ⇒ every tip `[]` ⇒ `0 < n` fails (`:399`) ⇒ each completion its own chain (`:124-128`); merge loop `range(1,1)` never runs, `kept == 1 == len(chain)` ⇒ `chains_reconstructed_full += 1` (`:261-262`) | N clean length-1 chains, `full=N, truncated=0`; COMPLETED |
| abort anywhere (P2) | build() | scan over ALL raw completions (`:145-147`) | status ERROR, whole session |
| P1 filters everything | build() | early return (`:103-116`) | ERROR "no trainable completions after completion filter" |
| P1 filters a chain TAIL | grouping input | filter runs before grouping; `kept == len(chain)` tested against the post-filter chain (`:261-262`) | chain counted "full"; amputation invisible except `completions_merged`/`completions_total` |

The finalize-loop's own canonical-prefix break (`:212-221`) is
**defensive dead code**: the grouping guard is the exact negation of the
break condition over the same consecutive pairs, and
`build_trace_from_completion` is deterministic — adversarially attacked
(ordering, longest-tip, equal tips, empty tips) with no counterexample.

**8. `attention_mask` / `position_ids` — not stored, derivable.** `Trace`
carries exactly `prompt_ids`/`response_ids`/`loss_mask`/messages/`tools`/
`finish_reason`/`response_logprobs`/`reward`/`metadata`
(`models.py:89-101`). The stream is a flat concatenation — the slime
adapter emits `tokens = prompt_ids + response_ids`
(`adapter.py:167`); no padding or packing exists anywhere Polar-side, so
both are derivable from lengths. Packing is the trainer's (slime-side),
out of scope by the scope law.

#### Step 3 — the registry seam and the recommendation

Verified end to end: config key `TaskRequest.builder` =
`StrategySpec{strategy, config}` (`rollout/models.py:59-71`, default

`rollout/models.py:88`), resolved at `node.py:628`;

(`_imports.py:11-30`), which enforces `issubclass(…,

(`registry.py:38`). **A `PrefixMergingBuilder` subclass in `gsj_rollout`
is selectable as `builder.strategy = "gsj_rollout.<module>:<Class>"` with
zero vendored edits**, provided `gsj_rollout` is importable in the
gateway process (A-14). The override surface is `async
build(self, session: CompletionSession) -> Trajectory` (`base.py:22`;

subclass receives the **full raw session** — ordered `CompletionRecord`s

callback payload does NOT carry. **It can genuinely reject**: returning

**Recommendation (written into checks-spec): both.** The builder
subclass runs session-level checks the receiver can never see

subclass imports them. CP-10/CP-11's checks land in **both** places;
neither alone suffices — the subclass sees what the wire drops, the
receiver sees what actually arrived.

#### Step 5 — THE VERDICT

**Is Polar's trajectory reconstruction trustworthy for our use?**

**GO WITH CONDITIONS.** Unhedged: the algorithm is the right one and the
code implements it faithfully — but the layer's universal failure mode is
to degrade **silently into a clean-looking COMPLETED trajectory**, and at
the pin nothing anywhere raises an error for any of it. Polar's
reconstruction is trustworthy **only** with the named conditions below;
without them it is not, and CP-03's live run already proved that in
miniature (10 degenerate chains reported `full=10, truncated=0`).

**Sound (cite the code):** the retokenization guarantee
(`record_utils.py:82-107`, `prefix_merging.py:337-353`; no tokenizer in
the builder); strict token-id prefix partitioning (`:397-401`); the
§3.4.2 interstitial split, faithful including the duplication-avoidance
branch (`:326-334`); mask/logprob alignment invariants (placeholders
never at `mask==1`, whole-array nulling, `:362-368`); the escalation-only
status path that makes builder-side rejection real
(`node.py:579-624`); the registry seam (`registry.py:45-52`,
`_imports.py:11-30`); the metadata channel surviving to callback and
slime (`node.py:860`, `adapter.py:141-160`); and all three carried
patches doing exactly what their headers claim in situ.

**Fragile, and under what conditions:** everything degrades silently to
COMPLETED — chain degeneration under missing token ids (S1), truncation
under EOT-unknown/absent/retry (S2/S3), fresh-chain splits under
compaction/edits (S4), EOT **misdetection** under stop-parameter finishes
(S5 — corrupted stream, correct-looking stats), stream gaps under partial
capture (S6), discard-and-reprompt training on thrown-away tokens (S7),
`choices[0]`-only capture (S8), and mixed-version merges presenting a
single version (S9). The stats snapshot alone cannot distinguish a
perfect episode from several of these; `response_messages` can silently
desync from the token stream (count-only `msg_acc`, `:197-198,246-254`).

**Missing — what we must supply:** (1) A-15: explicit
`end_of_turn_token_id` in the builder config, subclass fails closed when
unset — the only defense against S5 and half of S2; (2) the
`ValidatingPrefixMergingBuilder` subclass in `gsj_rollout` (CP-07;
session-level checks + ERROR rejection — S3/S6/S7/S8/S9, roster
stability, filter-drop review); (3) `checks.py` receiver rules
(CP-10/CP-11): the tightened G7 conjunction (`chains_total == 1` ∧
`truncated == 0` ∧ `completions_merged == completions_total` ∧
`raw_completions_total == completions_total`), the logprob discipline
including the empty-mask and absent-logprobs hard failures, the
`finish_reason` allowlist, G6 decoding token ids never messages; (4) the
A-12 re-validation of P1 against pi's wire dialect at CP-06, sharpened by
the key-presence fact; (5) harness config discipline: no `n>1`, no stop
parameters (subclass enforces `len(choices) == 1`).

**Unknowable without a real engine (CP-09's job):** whether vLLM/SGLang
include the terminal EOT token in returned `token_ids` per finish reason
— this decides which `_slice_interstitial` branch runs and therefore
whether the model's own end-of-turn decision is trained (`mask==1`) or
replaced by a canonical mask-0 copy; actual token-id and logprob fidelity
against the golden reference; `prompt_ids` presence under pi's engine
config; and every per-dialect fact about pi 0.83.0's traffic (A-2, A-12).

**No §9 abandon condition is met.** Every defect found has its fix in
**our** code — config, a zero-patch builder subclass, and receiver checks
— which is precisely the architecture the charter already mandates. Path
C (take `prefix_merging` as an algorithm, keep our own capture) is not
warranted by anything found here; its trigger remains a CP-09 fidelity
mismatch with no fix on our side.
