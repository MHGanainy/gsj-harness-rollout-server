**What the re-shape surfaced that the manifest key had been hiding.**
(a) v1 validated NOTHING at the corpus root — a stray `test/cases/`
tree, a typo'd `trian/`, anything, was silently ignored; the key hid
this because the split never depended on the tree's shape. Making the
split a directory property forced root strictness, which is where the
file-named-`train` hazard (finding 1) also lived: a one-line manifest
key cannot half-exist, but a directory can, so the validator had to
learn type checks the manifest form never needed. (b) The frozen
mcp-service suite consumes the corpus exclusively through the pipeline
API (`phase_validate` + `build_case_repo` + the lock fingerprint), so
the re-shape was invisible to it — 73/73 green with the bares rebuilt to
identical SHAs. CP-01's caveat 3 ("any future corpus change breaks mcp
tests by design") is measured NARROWER than recorded: path-shaped
changes don't break it; only content/census changes would. (c) git's
rename detection paired some identical-content `prompts.yaml` files
across cases in the move (e.g. `case_0001/timestep-12/prompts.yaml` →
`eval/case_0004/timestep-13/prompts.yaml`) — cosmetic, since all twelve
are byte-identical, but a reminder that the staging corpus's prompt
files carry no per-case content yet. (d) The split was the last reason
`load_corpus` needed the manifest to know anything about cases; with it
gone, corpus.yaml is purely estate/identity configuration and the tree
is purely content — a cleaner boundary than v1 had.
