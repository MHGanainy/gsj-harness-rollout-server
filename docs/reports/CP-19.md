## Notes

### The pins decision, and what a foreign estate actually experiences

**Taken: option 3 — ship as-is with a loud signal** (ADR-0019), the
prompt's recommendation, for the reason the prompt gives and one it does
not.

The reason given: it preserves the property CP-16 built and CI proves.
"Ship empty" is the option that *looks* most honest and is the most
destructive — it deletes the out-of-the-box trainer leg, invalidates the
CI job that guards it, and converts a working install into a
configuration error for every consumer including the only real one we
have (the slime bridge). Honesty that costs a working feature should buy
something; here it buys a `PinsConfigurationError` where a sentence would
do.

The reason not given, which decided the shape of the signal: **the
exposure was never a correctness risk, only a comprehension one.** Approval
is set membership. A foreign estate's trace does not sneak past our pins;
it collides with them, and the collision is per-gate and names the offending
digest — `G2:system_prompt_hash_not_approved:<digest>`,
`G3:tool_roster_hash_not_approved:<digest>`,
`G7:settings_hash_not_approved:<digest>`. There is no input for which
wrong pins produce a *pass*. So the cure had to be aimed at a reader's
belief, not at the gate's behaviour — which is why it is a `UserWarning`
and not a raise, and why nothing about the gates changed.

The signal fires **only in the case that is actually ambiguous**, and this
was verified in all three configurations rather than reasoned about:

| configuration | `PINS_PATH` resolves to | signal |
| --- | --- | --- |
| installed wheel, no `GSJ_PINS_PATH`, no checkout | the packaged copy | **warns** — the PyPI stranger, and the only ambiguous case |
| repo checkout | `pins/pins.gsj.json` | silent — a developer working in-tree |
| `GSJ_PINS_PATH` set explicitly | the override | silent — the operator has chosen |

A consumer with their own estate therefore does one thing: set
`GSJ_PINS_PATH` to their own pins file before the first import of
`gsj_rollout.checks` (they load once per process). A wrong or absent path
raises `PinsConfigurationError` naming it and never falls through to ours.
That instruction is now in three places a stranger might look — the
README's own section, `docs/checks-spec.md`'s operational facts, and the
warning itself.

**Sync and re-pin**, the sub-question Step 1 asks: the packaged copy
cannot drift from `pins/`, because it is force-included *from* it at build
time and never duplicated in the tree — there is no second file to go
stale. A re-pin therefore costs a **checkout** consumer nothing (the
checkout outranks the packaged copy in the resolution order) and costs a
**published artifact a rebuild**: pins are baked at build time, so a wheel
is a snapshot of the approved sets as of its build. A re-pin that must
reach installed consumers is a version bump, not a file edit.

### The licence, and how Polar's is kept distinct

**Apache-2.0** (ADR-0020), chosen over MIT for two reasons specific to
this tree rather than out of habit.

First, Polar is Apache-2.0. Matching it means the repository carries
**one** set of terms instead of two a reader has to reconcile, and the
awkward question — is `pi_harness.py` a derivative work of the thing it is
a thin shell over? — stops changing anyone's obligations, because the
answer is the same either way. Second, Apache-2.0 §4(b) makes "state that
you changed it" an obligation rather than a courtesy, and this repo
already practises exactly that discipline for the three carried patches
(`vendor/patches/P1..P3`, `vendor/REVENDOR.md`). Choosing a licence that
does not ask for it would have been choosing against our own habit. MIT's
simplicity buys nothing this project needs and drops the patent grant.

`LICENSE`'s terms body is byte-identical to `vendor/polar/LICENSE` —
verified by diff, not asserted; it is the canonical Apache-2.0 text, which
is meant to be copied verbatim. Only the appendix copyright line differs.

**How Polar's licence stays distinct: structurally, not textually.**
Nothing was appended to our `LICENSE` and no NOTICE file was invented,
because the two licences never meet in a released artifact. `vendor/` is
in **neither** the wheel nor the sdist, so nothing NVIDIA-authored ships
under this project's name, and there is no per-file attribution question
to answer for anything we distribute. In the repository, the vendored
subtree keeps its own `LICENSE` in place — the standard expression, and
the one a licence scanner already understands. The claim is asserted at
build time in `release.yml` rather than left as a paragraph, which matters
because it is the kind of claim that silently stops being true.

### What actually ships — and the sdist, which did not

The wheel was clean before this CP and is clean now. **The sdist was
not**, and this is the finding of Step 3.

`python -m build` with no flags — the command in the DoD, and the one any
contributor runs — produced a **4.6 MB, 835-file** tarball containing
`vendor/` (215 entries, including `vendor/polar/LICENSE`), `corpus/`,
`mcp-service/`, `forgejo/`, `spike/`, `staging/`, `.claude/`, `docs/` and
`tests/`. The backend's default root set is "every tracked path". One
`twine upload dist/*` — the standard idiom — publishes all of it under
this project's name.

The first fix did not work, and that is worth recording because it looks
like it does. Stating an explicit `include` list left the sdist **still**
carrying `vendor/polar/LICENSE`, `vendor/polar/pyproject.toml` and 20
vendored `README.md` files: hatchling applies its default file selection
*on top of* `include`, and that selection globs README/LICENSE/pyproject
**recursively**. `only-include` narrows the root set instead of extending
it, and is what landed. Measured both ways rather than reasoned about —
had this been left at `include`, the stanza would have read like a guard
while shipping an NVIDIA licence file with no NVIDIA source for it to
apply to.

Publication is **wheel-only** regardless (ADR-0020): the package is pure
Python, no consumer needs to build from source, and the real source is a
public repository named in the metadata. The sdist stanza is the second
guard — it protects the operator's local `dist/`, which wheel-only
publication does not.

### Metadata: two claims removed for being untrue

`readme`, `license`, `license-files`, `classifiers` and four `[project.urls]`
landed as Step 2 asks. Two entries were *withheld*, both because they
would have been false:

- **No `License ::` classifier.** PEP 639 forbids pairing one with the
  SPDX `license` expression; the combination is rejected. The METADATA
  carries `License-Expression: Apache-2.0` and `License-File: LICENSE`
  instead, which is the modern form and what `twine check` validates.
- **No `Typing :: Typed`.** That classifier asserts PEP 561, which
  requires a `py.typed` marker inside the package. There is none, and
  adding one is a `gsj_rollout/` change this CP is not lifted for. It was
  in the first draft and removed on verification — a one-line lie that
  would have told every type-checker to trust annotations the package does
  not ship a marker for.

**`requires-python` narrowed `>=3.11` → `>=3.12`**, the prompt's "simpler
honest move", taken over adding a 3.11 CI leg. Nothing ever ran 3.11: CI
is 3.12, every deployment target is 3.12 (the mcp-service image, Polar's
uv venv, the H200 collector), and the operator's workstation is 3.13. A
floor nothing tests is a promise, not a fact. 3.13 is claimed by
classifier on real evidence — it is the interpreter the root suite runs
under every checkpoint, including this one.

The README was rewritten as a landing page as well as a front door,
because on PyPI it is the project page: it now opens by saying what the
thing is, names the **two-roles** split (the published package is the
trainer leg; the server leg needs an estate and `pip install` does not
change that), glosses `CP-NN` for someone who has never seen this repo,
carries the packaged-pins statement, and has a Licence section. Its links
were made **absolute** — relative markdown links resolve on GitHub and
404 on PyPI, which would have broken every pointer on the page this CP
exists to produce.

### The release workflow: its permissions, and what it refuses to do

`.github/workflows/release.yml`, triggered on `v*` tags and on
`workflow_dispatch`. Three jobs: build-and-prove → TestPyPI → PyPI.

**Permissions**, which is the note CP-18 left for this CP. CP-18 declared
none because no job used the token beyond `actions/checkout`'s read; this
one declares `permissions: {}` at the top — default-deny — and grants per
job: `contents: read` on build, `id-token: write` on the two publish jobs,
nothing anywhere else. `id-token: write` is there because publication is
via **trusted publishing**: an OIDC exchange, so no API token is stored in
this repository and none has to be rotated. The publish jobs do not check
the repository out at all; they download the artifact the build job made.

**What it deliberately does not do**, stated in the header the way CP-18's
is:

- **It does not re-run CI.** No corpus suite, no mcp-service suite, no
  matrix. Those guard components that are in no artifact. What it re-runs
  is the wheel job *only*, because that job's subject **is** the thing
  being published. The prompt offered "depend on the tests having passed"
  as the alternative branch; it was not taken, and the header says so
  plainly rather than implying a coverage it does not have: the tag is
  *expected* to point at a CI-green commit, and nothing in the workflow
  enforces it.
- **It does not publish an sdist.**
- **It cannot reach PyPI from a rehearsal.** The PyPI job is gated on the
  ref being a `v*` tag *as well as* on `needs: testpypi`, so
  `workflow_dispatch` exercises the entire path — build, assertions,
  `twine check`, install proof, a real TestPyPI upload — with no route to
  the real index. That is the "documented dry-run path" Step 4 asks for,
  made structural instead of documented.

Two guards that exist because their failure is silent: a **tag-vs-version**
check that runs before anything is built (a tag disagreeing with
`pyproject.toml` publishes the wrong number under the right name, and
neither PyPI nor pip will ever mention it), and the **exclusion
assertions** on every release rather than once in this report.
`skip-existing: true` on TestPyPI, because a rehearsal may be repeated;
deliberately **absent** on PyPI, where a version that already exists means
the release is confused about what it is publishing.

Rehearsed the way CP-18 rehearsed its own: the steps, not the YAML.
`python -m build --wheel`, the exclusion assertions, `twine check`, and
the install proof all ran locally and pass. The job wiring, the action
versions and the OIDC exchange are proven by nothing yet — no run exists.
One version guess was caught in that pass and corrected against the
registry rather than shipped: `upload-artifact`/`download-artifact` are at
majors **v7** and **v8** respectively, not the v6 first written; the
pairing is the one their own README documents.

### The publish decision

**Not published.** Asked, not defaulted — the same call CP-18 made when
its DoD required an action only the operator could authorise.

The recommendation in the prompt was to publish, and the argument for it
is sound: 0.1.0 is real, the trainer leg is proven, and an unpublished
release path rots. What stops it is not doubt about the pins decision or
the licence — both are settled above — but two facts that are not
arguments about readiness:

1. **It cannot be done from here.** Trusted publishing requires a pending
   publisher created in the PyPI and TestPyPI web UIs under the owning
   account. There is no API token in this environment, no `~/.pypirc`, and
   no `TWINE_*` in the environment (checked). A tag pushed today fails at
   the OIDC exchange with `invalid-publisher` — correctly, since nothing
   has authorised anyone to publish this name.
2. **It is irrevocable.** PyPI refuses re-upload of a version even after a
   yank. The only cure for a wrong 0.1.0 is 0.1.1. Building the path is
   reversible; publishing is not, and the asymmetry is the whole reason
   the workflow rehearses on TestPyPI first.

**The standing cost, stated because it is the real one: the name is not
reserved.** `gsj-harness-rollout-server` is unclaimed on both indexes —
verified through the JSON API (404 for it, 200 for `httpx`), because the
HTML project pages sit behind a bot challenge that returns **200 for names
that do not exist** and is therefore not an oracle. Anyone may claim it
before we do. That risk is accepted rather than overlooked; the
alternative is an irrevocable upload made to win a race, which is a worse
trade than losing the name.
