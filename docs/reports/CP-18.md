Two details are the whole reason job 3 and job 4 are not one-liners:

- **`mcp-service/.venv` is the only path that works.** `tests/helpers.py`
  spawns every server subprocess through `PYTHON = SERVICE_DIR / ".venv"
  / "bin" / "python"` — a hardcoded interpreter. Installing into the
  job's ambient Python would produce a suite that collects fine and then
  fails to start a single server. This is exactly the prompt's predicted
  "anything assuming a venv path"; it is a finding about the test, and
  the CI accommodates it rather than editing it (`tests/` is frozen, and
  would be regardless — the assumption is reasonable for a component that
  ships its own venv).
- **The install proof must run from outside the checkout or it proves
  nothing** — for a more mundane reason than the pins resolver.
  `checks.CHECKOUT_PINS` is module-relative
  (`Path(__file__).resolve().parent.parent`), so cwd cannot make the
  checkout's `pins/` win for an installed package; that path simply does
  not exist beside `site-packages/gsj_rollout/`. The real hazard is one
  level up: with the repo as cwd, `import gsj_rollout` binds to the
  **source tree**, and the job would then validate the checkout and say
  nothing whatever about the artifact — passing happily on a wheel that
  ships no pins at all, which is the CP-11b state CP-16 fixed. Hence
  `$RUNNER_TEMP`, the `cd`, and the two assertions that run before the
  validation: `PINS_PATH == PACKAGED_PINS` and `site-packages` in its
  parts. Those are what detect a source-tree import; the `cd` alone would
  be a convention, not a check.

### What broke — the honest version

**Nothing broke on the runner.** That is a weaker statement than it
looks, so here is the part worth reporting: the first CI run was not the
first execution. Every job's steps were rehearsed first in a Linux
`python:3.12` container — the commands each job runs, executed as a
non-root user against a `git archive` of the exact staged tree, so a
fresh checkout is what they saw (no `.venv`, no caches, no built bares,
no git identity). That is a rehearsal of the steps, not of the YAML:
nothing local executes a workflow file, so job wiring, action versions
and `working-directory` were proven only by the run on GitHub. The
rehearsal broke twice. Both breaks were environment-dependent, both were
diagnosed rather than routed around, and **neither produced a fix
anywhere** — the workflow that ran on GitHub is byte-identical to the one
written before the rehearsal, with no test, no fixture and no frozen path
touched.

1. **The receiver's atomic-batch test fails when the suite runs as
   root.** `tests/test_receiver.py::test_a_staging_failure_leaves_no_partial_batch_and_no_orphan_tmp`
   chmods the staging directory to `0o500` and expects the write to fail
   (→ HTTP 500). Root has `CAP_DAC_OVERRIDE`, so the write succeeds and
   the assertion sees `200 == 500`. My first rehearsal container ran as
   root; re-run as a non-root user, the suite is 129/129. Hosted
   `ubuntu-latest` runs as the non-root `runner` user, which is why CI
   never saw it. Recorded because it is a live trap for anyone who later
   runs this suite in a `container:` job or a Docker build (both root by
   default) — the test would fail there, correctly reporting that its
   premise, a real permission denial, does not hold.
2. **One mcp-service test's bit-exactness oracle is
   architecture-dependent.** `tests/test_backend.py::test_stored_vectors_are_the_pinned_encoders`
   asserts the stored Chroma vector is bit-identical to a fresh encode of
   the same chunk. On `linux/arm64` it fails (`-1.07737631e-01` stored vs
   `-1.07737623e-01` re-encoded); on the x86_64 runner it passes, which is
   why CI is green. The property the test guards — that the pinned MiniLM
   embedded the corpus and Chroma's default ONNX embedding function never
   touched it (ADR-0016's named hazard) — is intact on both, measured
   rather than asserted: over `case_0001`'s 51 chunk vectors on arm64, 36
   are bit-identical and the rest differ by **at most 1 ULP** (worst
   |Δ| = 1.490e-08, worst `cosine(stored, ours) = 0.999999940`), while a
   *wrong* embedder lives seven orders of magnitude away — the cosine
   between two different chunks' vectors in the same index is 0.80. The
   encoder is deterministic in-process (a second `encode_corpus` of the
   same texts is bit-identical to the first, measured), so the divergence
   is in the storage round-trip, not the model; our vectors' norm is
   1.00000011920929 rather than exactly 1.0, which is enough for any
   normalisation on the way in to move every component by an ULP. The test
   is stricter than the
   property by design and that is usually right; it just means this suite
   is x86_64-and-macOS-verified, not portable-by-assertion. **No action
   taken**: `mcp-service/` is frozen, CI is green on the architecture CI
   runs, and a deselect would have traded a real guard for an
   architecture this project does not deploy on. Filed as a finding, not
   a change.

Both are instances of the prompt's own prediction — "anything that passes
locally because of state your machine has and a runner doesn't" — with
the sign reversed: these pass on the runner and on the operator's Mac,
and fail in a third environment nobody had tried.

### The mcp-service decision, with its reasoning

The prompt flagged job 3 as "the one that may not work as-is" and offered
three outs: cache the model, split it into a slower job, or exclude it
with the reason recorded. **None was needed — it runs as-is, in the same
workflow, on every push.** The measurements behind that:

- **Runtime**: 187s end to end — **77s** of install (torch 2.13.0+cpu,
  chromadb 1.5.9, sentence-transformers 5.7.0 and their transitive
  dependencies: ≈349 MB of wheels, torch alone 191.8 MB), **96s** of
  pytest (93.73s inside the suite), and ~14s of setup, cache-save and
  teardown steps. Against a 30-minute job timeout that is not a "slower
  separate job"; it is the other three jobs combined plus a minute of
  pip.
- **Network**: needed twice — PyPI plus the pytorch CPU index for the
  install, and HuggingFace for the pinned MiniLM at first embed. Hosted
  runners have both. Nothing else in the suite reaches the network: the
  bares are built locally through the pipeline's `file://` rail, the
  servers are localhost subprocesses, and Forgejo is never contacted.
- **Caching**: taken, and only here — the prompt's "no caching beyond
  what job 3 genuinely needs" read as a bound on *where* caching may
  appear, not as a claim that job 3 would fail without it. Run 1 was a
  cold miss on both and still finished in 187s, so both are economies.
  The pip cache is keyed on `requirements.txt`. The HF cache key repeats
  the pinned revision as a **literal**, which the report's first draft
  called "correct-by-construction (a re-pin misses)" — it is not, and the
  verification pass said so: re-pinning `config.yaml` does not invalidate
  the key. It also does not have to. HF's own cache is keyed by revision
  internally, so a stale hit simply lacks the new snapshot and downloads
  it; the cost of forgetting to update the key is a cold-ish cache, never
  a wrong model. The comment in the file now says exactly that.
- **The one thing it does need**: the venv at `mcp-service/.venv`,
  because the suite's helpers hardcode that interpreter (above).

Recorded consequence: the model download is the single external
dependency in this CI, and the only step that can turn the badge red
without a code change. It is one job of four, and its failure mode is
loud.

### What CI deliberately does not do

Named here so the omissions are decisions with reasons, not oversights a
later reader has to guess at. Each came out of the CP's verification pass
as a candidate defect and was answered rather than absorbed.

- **It does not pin its own dependencies.** Three jobs install unpinned
  (`pip install -e ".[dev]"`, `pytest pyyaml`, `build`), so the same tree
  can be green today and red next month on a dependency this repo never
  chose. That is not a CI defect: `pyproject.toml` declares `pydantic`,
  `httpx` and `pyyaml` with no constraints, so unpinned resolution is
  precisely what a consumer installing this package gets, and pinning CI
  would test a configuration the package does not describe. The component
  that *is* pinned exact — `mcp-service/requirements.txt`, contract-pinned
  since CP-15 — is installed from that file, pins and all. If the floating
  half is ever to be pinned, `pyproject.toml` is where it happens and CI
  follows, not the reverse.
- **It does not assert the counts in its job names.** Every job runs a
  bare `pytest -q`, which exits 0 for any number of passing tests, so a
  collection change that silently drops tests leaves the badge green under
  a job still called "root suite (129)". The counts are documentation, not
  gates. The cheap fix exists (compare `pytest --collect-only -q | tail -1`
  against an expected number) and was not taken this CP: the prompt asked
  for small, and a count gate is a second thing to maintain. Recorded as
  the honest limit of what green means.
- **It sets a timeout only where a hang is plausible.** `timeout-minutes:
  30` is on the mcp-service job — the one that downloads a model and
  binds sockets. The other three finish in 13–38s and inherit GitHub's
  360-minute default, which is a backstop rather than a hazard on a repo
  with no scheduled runs and one contributor. No `concurrency:` group, for
  the same reason: `push` is main-only, so the duplicate-run case a
  concurrency group exists to cancel does not arise here.
- **It does not run `vendor/polar/tests`.** That is the one real hole in
  "the fixture-driven half", and the verification pass found it:
  `vendor/REVENDOR.md` step 5 makes four carried-patch tests
  (`test_record_filters.py`, `test_builder_filter_wiring.py`,
  `test_prefix_merging_abort.py`, `test_storage_policy_version.py`)
  mandatory verification, they are fixture-driven, and a hosted runner
  could run them. What stops them is that they need Polar's own uv venv
  and belong to the re-vendor recipe — a procedure that runs at a
  re-vendor, not on every push. The caption and the header now name the
  omission instead of letting "the fixture-driven half" imply coverage,
  and wishlist row 16 carries the fifth job for whoever wants it.

### Verification: a 4-lens adversarial pass, 25 findings, 8 confirmed

Four independent reviewers (workflow correctness and "green while wrong" /
caption and badge honesty / charter-register-wishlist consistency / this
report against reality), every finding then handed to a separate verifier
instructed to **refute** it and to re-execute the check itself: **25
raised, 8 confirmed, 17 refuted**. All 8 were fixed before the commit,
and every one of them was a claim in a document rather than a defect in
the pipeline — which is the correct shape for a CP whose executable
surface is 146 lines of YAML that had already run green.

What it caught, in descending order of how wrong I was:

1. **The wheel job's stated safety mechanism was simply not the
   mechanism.** Both the report and the workflow comment said running
   outside the checkout is what stops `PINS_PATH` resolving to the
   checkout's `pins/`. It isn't: `CHECKOUT_PINS` is `__file__`-relative,
   so cwd cannot affect it. A verifier built the real wheel, installed it
   outside the checkout and probed the resolver to establish this. The
   real hazard is a source-tree *import*, and the two assertions in the
   proof script are what catch it. Corrected in both places.
2. **"Every environment this project runs is 3.12" was false** — the
   operator's own venv is 3.13 and the package declares `>=3.11`. Now
   stated as *deploys into*, with the uncovered interpreters named.
3. **The caption overstated the barrier**: episodes were said to need
   "a GPU, the H200 estate and cluster time", which this README
   contradicts two paragraphs down (CP-07/CP-09 ran real episodes on the
   Mac estate). Now: an episode needs an estate; the governing numbers
   need the H200.
4. **The mcp-service install time was fabricated by a factor of two** —
   "2m 30s" against a measured 77s, in a decomposition that exceeded the
   job's own 187s wall clock. Also "~310 MB" of wheels against a measured
   349 MB.
5. **"Correct-by-construction" was not**: the HF cache key is a
   hand-copied literal, so a re-pin does *not* invalidate it. The
   workflow comment and the report now say what it actually guarantees.
6. **The charter said the mcp-service suite was 83** in two places, while
   CP-15's own report says 89 and 73 + 16 = 89 — a pre-existing typo my
   new paragraph would have sat next to, contradicting it. Corrected in
   both, marked as corrected.
7. **"The fixture-driven half" was one suite short of true**:
   `vendor/polar/tests` — including the four carried-patch tests
   `REVENDOR.md` makes mandatory — is not run. Now named as an omission
   in the header, and wishlist 16.
8. **The two-SHA paragraph and the `files:` stat described a state that
   did not exist yet.** Rewritten to describe what the amend actually
   does, with the comments-only proof run rather than asserted.

Refuted, for the record: that unpinned CI dependencies are a defect (they
mirror `pyproject.toml`, which is what a consumer gets, and the pinned
