#### The harness contract as landed (ADR-0006) — the settings keys

`AgentSpec.settings` is the whole input channel. Required:
`case_id`, `timestep`, `clone_url_for` (Forgejo URL pattern with
`{case_id}`), `mcp_url_base`, `tools_allowlist` (the roster **list** — the
row-31 fix), `artifacts_dir`. Optional with defaults:
`mcp_token_secret_env` (`GSJ_MCP_TOKEN_SECRET`), `mcp_token_ttl_s` (3600),
`workdir` (`/workspace` — keeps the G2 docker singleton), `pi_entry`,
`pi_mcp_extension`, `context_window` (32768), `max_tokens` (8192),
`thinking` (`off`). `model_name` stays `provider/model`
(`gsj/Qwen/Qwen3-0.6B`). `setup()` validates the contract loudly, captures
`runtime.session_id`, clones `case_0001` at `timestep-12`, and writes pi's
agent-dir config; `run_steps()` mints the token, renders `.pi/mcp.json` +
models.json (the two exec-time substitutions), and emits the ADR-0008
argv; `postprocess()` downloads the transcript and `out/`.

#### The token mint and where the secret lives (ADR-0006)

Minted host-side in `run_steps()`, stdlib HS256 (the
`corpus/ingest_corpus.py:797-810` ADR-0041 recipe — PyJWT deliberately not
added to Polar's venv, A-14), claims exactly
`{case_id, timestep, episode_id, exp}` with `episode_id` = the Polar
session id and `exp = now + ttl`. The secret is read from the gateway
process env (named by `mcp_token_secret_env`) at mint time and appears in
no argv, log, or metadata — only the signed token, in `.pi/mcp.json`'s
URL. The claim `episode_id` = session id is load-bearing twice: it is how
the MCP `tool_call` log joins to the Polar session, and it is inside the
signature so the agent cannot repoint the token at another episode.

#### What pi-plus-MCP-under-Polar surfaced that CP-06's stub could not

1. **The glue-stitch defect (the headline).** pi's Qwen3 no-think template
   appends the empty think block `[151667, 271, 151668, 271]` to every
   generation prompt but not to the history re-render, so consecutive
   prompts are never token-prefix-stable and the vendored grouping opens a
   fresh chain per turn — 2 clean "full" chains, silently COMPLETED (the
   S4 shape). The stub tokenized bytes with no template, so it was
   structurally incapable of showing this; it took an end-to-end episode.
   Fixed in the subclass (ADR-0007, A-21): a config-pinned,
   strict-extension prompt-ids stitch before grouping. Same episode then
   `chains_total == 1`.
2. **The engine tool-parser requirement.** pi sends `tool_choice: auto`;
   vllm-metal 400s (`"auto" tool choice requires --enable-auto-tool-choice
   and --tool-call-parser to be set`) — the first submit ERRORed "no
   completions" until the engine was restarted with those flags. The
   proxy forwards `tool_choice` untouched, so this is an engine-config
   requirement, not a translation failure — the H-41 dependency from the
   vLLM side. CP-09's bring-up must pin it.
3. **Two container-filesystem traps in the harness.** pi's managed-binary
   installer (rg/fd into `<agent dir>/bin`) renames across filesystems, so
   a session-bind-mount agent dir silently breaks the built-in grep/find;
   the agent dir must be container-local (`/tmp/pi-agent`, also
   non-root-safe for the uid-1000 image). And `PI_OFFLINE=1` (the spike's
   carry-over) gates that download regardless of the `--offline` flag —
   unset, so pi fetches rg once per episode. The golden reference hit the
   same grep-ripgrep failure (its `--offline`/ro-`/agent` path), so the
   built-in tool mix is faithful to it.
4. **The mcp.json load-order and shape are unforgiving.** `.pi/mcp.json`
   must exist under pi's cwd at launch (the extension reads cwd at module
   load and bails silently if absent), `lifecycle: eager` is mandatory in
   print mode, and the server key `gsj` + toolPrefix `mcp` are what
   produce the `mcp_gsj_*` names the roster and G3 depend on. All rendered
   in `run_steps()` and confirmed live: 11 tools offered, all four MCP
   tools executed ok.
5. **The real callback body must be fetched, not read from disk.** The
   on-disk `ses_*.json` strips `trajectory.status`/`error`; the true
   `SessionResult` (status COMPLETED, findings `[]`, `gsj_validation` and
   `reconstruction_stats` intact) came from `GET /rollout/task/{id}` —
   the receiver at CP-08 must validate the POSTed body, never reconstruct
   from rollout disk (row 16 restated, now with a real payload).
6. **The metadata channel works end to end for our findings.**
   `gsj_validation` (builder id, `findings`, `glue_stitched`) rode the
   callback verbatim, never touching the reserved `evaluation` key —
   the CP-05 seam, exercised on a real trajectory.
