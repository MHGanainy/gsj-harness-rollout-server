### §2 verl's bring-up, and what it needed that the estate did not

1. **A venv, not a runtime.** verl 0.9.0.dev @ `1ae9455` (`bridge.VERL_SHA`,
   `--no-deps` from git) + torch cu126 + the CP-20-proven pins in a host
   python3.12 venv. No image, no firewall dance, no Ray cluster — because
   the classic-feed harness needs no Megatron and no rollout engine. The
   slime loop's hardest bring-up item (24.4 GB image through the
   uid-scoped firewall) has no verl counterpart.
2. **The CUDA variant by hand**: torch 2.13.0's default PyPI wheel is
   cu130; the box's driver speaks 12.8 → "driver too old" at first
   import. The cu128 index carries no 2.13.0; **cu126 does** —
   `torch==2.13.0+cu126` cured it.
3. **The fit-loop import closure**: `--no-deps` leaves the trainer-side
   modules' imports unstated — observed `ModuleNotFoundError` chain:
   `torchdata`, `datasets`, `PIL` (pillow), `cachetools` (+ `tqdm` on the
   same import path); `wandb`/`tensorboard`/`pylatexenc` installed only to
   quiet pip's declared-dependency warnings.
4. **F-12** (external register): verl's own v0 batch-conversion helper
   (`left_right_2_no_padding`) hard-requires flash-attn — a lazy
   `flash_attn.bert_padding` import with **no torch fallback** — on a
   host with no nvcc and no flash-attn wheel. The engine's flash-free
   branch (`use_remove_padding=False` + sdpa) is supported and was used;
   the helper is reproduced in pure torch in the harness,
   contract-asserted row by row. The desk-read also found the adjacent
   trap before it could burn a run: rmpad-under-sdpa silently attends
   ACROSS packed sequences (wrong logprobs, no crash).
5. **F-13** (external register): `entropy_from_logits_with_chunking` is
   dead config on exactly that non-rmpad branch
   (`transformer_impl.py:1418` unchunked vs `:1310` chunked) — the
   full-vocab entropy temporaries of a 30.7k-token padded micro-batch
   OOM'd the H200 **twice** (114/106 GiB in use at the raise), with the
   flag set. Cure: the entropy metric dropped from the recompute
   (decorative; the loss never computes it at entropy_coeff 0).
6. **Co-residency**: serve GPU 3 (~45 GB @ 0.30 frac — still under our
   CP-17-era hold), train GPU 7 (peak 71.3 GiB allocated). One box,
   disjoint devices, no interference observed; the post-sync healthcheck
   passed. GPU 5 — CP-17's training GPU — is now co-tenanted (~118 GB of
   other tenants), re-confirming the standing rule: discover GPUs at run
   time, never assume last checkpoint's map.

### §7 The verdict

**Does the loop close with verl? YES, WITH FINDINGS.**

Every step evidenced: **collect** (112 submissions, 110 qualifying,
zero rejections/quarantines, cutoff held) → **convert** (110 → one real
`DataProto`, three assertions live, `checks` trainer-side from the
packaged pins) → **train** (one real verl optimizer step:
`pg_loss −0.0944`, `grad_norm 2.32→clip 1.0`, non-degenerate reward
1/110, group-centred advantages −0.095…+10.39, captured logprobs
load-bearing via sequence-TIS) → **sync** (verl's own HF export served
by the estate engine; proven by a zero-noise probe moving 6,541/6,768
positions + the engine's reported root + a 310/310 one-step-exact weight
diff) → **collect again** (8/8 qualifying, converting clean, against a
demonstrably different policy).

The findings, each with a cost and an owner:

| finding | cost | owner |
| --- | --- | --- |
| **F-12** — verl's v0 batch-conversion helper hard-requires flash-attn (no torch fallback) even when the engine runs its flash-free branch | a flash-attn-less host cannot run the classic fit loop as written; ~40 lines of contract-asserted pure-torch reproduction | **verl**; workaround ours |
| **F-13** — `entropy_from_logits_with_chunking` is dead config on the non-rmpad branch; padded-width logits + unchunked entropy OOM'd an H200 twice | one lost cluster-hour; the entropy metric dropped from the recompute | **verl**; workaround ours |
| **reward sparsity at 0.6B, worse than F-16's rate** — identically zero at 28 and 56; 1/112 at full cost | the collection cost 4× its stated budget (~45 min extra, parallel submission absorbed most of it) | **corpus/evaluator** (a denser grader or a stronger actor — CP-17's item 3, reconfirmed) |
| **the clipped step** — grad_norm 2.32 vs clip 1.0: a sparse-reward GRPO step at this scale leans on gradient clipping | visible and bounded (verl's own metric), unlike F-08's silent 1e6 — but a real run should tune, not clip | **trainer config** |
| **post-sync distribution narrowing** (§6) — entropy/KL controls off by design in a one-step loop | one more step in this configuration would deepen the collapse; a real run turns verl's controls on | **trainer config** |

**The milestone's question — two trainers, two loops: did the boundary
hold? YES, measured.** Neither loop needed anything of this repo:
CP-17's loop changed `docs/**` + `staging/**` (estate recipes); CP-21's
changed **`docs/**` only** — the staging recipes ran a second trainer
unmodified, `serve-updated.sh` served a verl export as readily as a
slime one, and the same wheel fed both bridges from the same callback
surface. What the second loop proved that the first could not: the
**server-side surface is trainer-shape-invariant in practice** — per-
sample objects (slime) and padded uid-grouped batches (verl) both came
from the same traces with zero server changes; the sync recipe is
trainer-agnostic (any HF-format export serves); and the failure classes
that did appear (F-12, F-13, reward sparsity, clipping) are all
trainer-side or evaluator-side, none at the boundary. The
trainer-agnostic claim is now **measured, not argued**.
