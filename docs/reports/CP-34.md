## Notes

### 1. The Polar decision, with what was measured (Step 1 → external ADR-0001)

**A published container** (`ghcr.io/mhganainy/gsj-polar:f0e8343a-gsj0.1.2`),
decided on measurement, not on the prompt's recommendation:

- `pip install` of the public library repo's `vendor/polar/` tree (pinned
  ref, patches P1–P3 already committed) into `python:3.12-slim` resolves —
  fastapi 0.141.1 / uvicorn 0.52.3 / pydantic 2.13.4 at build time.
  Polar's bounds are floors, so the image tag IS the effective pin (A-28).
- **The wheel gets in from PyPI, pinned** (`==0.1.2`), into the SAME
  interpreter; `import_path` then resolves with no PYTHONPATH —
  `issubclass(PiHarness, BaseHarness) == True` measured in-container.
  A-14's "Polar's venv hosts gsj_rollout", realized as one image.
- Both processes boot as separate compose services and find each other by
  DNS — after one measured failure: with no `rollout.public_url`, Polar
  defaults the gateway's registration target from `host:port` and the
  gateway dials `127.0.0.1:8080` inside its own container. With
  `rollout.host: 0.0.0.0` + `public_url: http://polar-rollout:8080` in the
  generated config: `/health` → `{"status":"ok","nodes":1}`.
- **DooD**: Polar's DockerRuntime shells out to `docker create/start/
  exec/cp/rm` and moves content by `docker cp` — no content-bearing host
  bind-mounts for our harness (read, then measured: a sibling container
  started from inside the image through the mounted socket). The one
  bind-mount it makes (the per-session dir) is handled by path identity:
  the host sessions dir mounted at its own absolute path + `TMPDIR`.
- **`GSJ_PINS_PATH` reaches both law-6 legs**: compose env
  `/estate/pins.gsj.json` on the gateway and the receiver; the printed
  submit one-liner carries the same variable for the trainer leg.
- The clone option was thereby dominated (the container works and is
  cheap); the manual option leaves F-45's seam open. Single-platform
  builds are FATAL, measured at the smoke: the Apple-Silicon-built image
  died `exec format error` on the amd64 box — the published image is
  multi-arch (amd64+arm64) and the Dockerfile's build recipe says why.

### 2. The stranger's three inputs, and the config that proves it (Step 2)

A corpus in the contract's shape; an inference endpoint; a `config.yaml`
of exactly this:

Everything else the library's CP-25 classification calls an estate fact

command in the comment). The engine legs are stated in the example and
in `up`'s final printout: a tool-call parser, a window ≥ the config's,
and the silent one — pinned sampling defaults, since pi sends none.

### 7. What a stranger still has to know that the README does not say — CP-35's hunt list

1. **Their endpoint is the wild card**: the smoke's engine was the
   reference stack. A non-vLLM parser, unpinned sampling defaults, a
   non-Qwen tokenizer (G6 tail, `end_of_turn_token_id`, estate-side G4)
   — each is a distinct way the first episode differs or rejects, only
   the last of which the bootstrap currently warns about by name
   (wishlist 35's walk is the durable answer).
2. Until the operator flips the two GHCR packages public (wishlist 34),
   the pull step fails for anyone unauthenticated.
3. The estate publishes NO host ports — reading traces means the
   bind-mounted `work/traces/`, and talking to the estate means joining
   the docker network; a trainer-side consumer on the host may want a
   published rollout port (a deliberate CP-35 question, not an oversight).
4. `finish_reason: length` on small models: the demo's 0.6B reference
   engine hits the 8192 cap on brief-shaped tasks — visible in the
   ADR-0025 line, worth a README sentence once CP-35's walkthrough shows
   real trajectories.
5. Disk and time expectations: ~3.5 GB of images, ~2.5 min cold `up` on
   an empty docker host, ~10 s warm.
6. `docker compose` v2 and a socket the invoking user can reach are
   assumed; rootless docker and remote contexts are unmeasured.
